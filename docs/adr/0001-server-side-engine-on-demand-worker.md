# エンジンはサーバーで動かし、オンデマンドの Worker で解析する

Stockfish は Visitor のブラウザ（WASM）ではなく、サーバーで実行する。ブラウザで解析するツール（Lichess の盤面解析など）が多く、そちらがよくある選択肢だが、次の理由でサーバーを選んだ。

- Analysis を Game ごとに保存し、共有 URL で誰でも同じ Game Review を見られるようにする。
- 初心者が使うスマホは性能がまちまちなので、解析時間をそれに左右させない。
- GPL の Stockfish をブラウザに配らずに済み、頒布に伴う義務を考えなくてよい。

その代わりに、計算費用はこちらが持つ。費用を抑えるため、構成は次のようにする。

- 同じアプリのイメージを、Web（常時起動の shared CPU）と解析 Worker（dedicated CPU）に分けて動かす。Worker を shared CPU にしないのは、CPU クォータのせいで Stockfish の速度が読めなくなるからだ。
- Worker は解析ジョブがある間だけ起動し、なくなったら停止する。Fly の auto start は HTTP リクエストをきっかけに起動する仕組みで、長時間のジョブとは合わないので使わない。
- 探索の深さと MultiPV を固定し、全体の日次上限を設けて、総量の上限を保証する。

## Consequences

- アプリは1つのコードベースのモノリスのままにする。マイクロサービスに分けたわけではない。
- ブラウザでの解析に戻すと、保存・共有・コストの前提がすべて変わる。
