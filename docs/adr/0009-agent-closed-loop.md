# マージまでこの PC の Claude Code が行う閉ループにする

Issue の実装・確認・レビュー・修正・マージを、ユーザーが使っているこの PC の Claude Code のセッションが行う。D15 の「マージは必ずユーザーが行う」を覆す（D95）。ユーザーはコードを読まず、品質はエージェントのレビューで保ち、変更の中身は Issue の要約で把握する（D93、D94）。GitHub はコード管理に使い、エージェントはクラウドでは動かさない（D116）。

人の承認の代わりに、次の関門をすべて通ったものだけをマージする。

- ローカルの lint・型・ユニットテスト・Docker 上の E2E
- 実装の文脈を持たない別のサブエージェントのレビュー（観点はリポジトリ内のスキルで版を管理する）
- GitHub Actions の CI（保険。D117）

ユーザーに確認するのは、次の場合だけにする。

- 権限・判断の記録・費用・関門に関わる場所（ADR と台帳の既存の記述、fly.toml、レビューの観点のスキル）を変えるとき
- エージェントが判断に迷ったとき（台帳や ADR との矛盾、方針や費用に関わる曖昧さ、修正が収束しない、本番で失敗した、など）

## Considered Options

- 人がすべての PR をレビューしてマージする（D15）：ユーザーがボトルネックになり、コードを読まないという目標と両立しない。
- GitHub Actions 上のエージェントと専用の GitHub App で回す：ユーザーが求めたのはクラウドでの作業ではなく、承認もこのセッションで行いたい。仕組みも複雑になる。

## Consequences

- ループは、ユーザーが指示した分だけ回る（D119）。勝手に次の Issue を選ばない。
- テストを弱める変更は、レビューで常に blocking にする。
- 誰がいつ何を変えたかは、Issue の本文の末尾の「## 結果」で追う。
