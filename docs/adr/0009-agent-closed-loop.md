# マージまでエージェントが行う閉ループにする

Issue に agent ラベルが付いたら、エージェントが実装し、CI と別のエージェントのレビューを通し、マージしてデプロイするところまでを人を待たずに行う。D15 の「マージは必ずユーザーが行う」を覆す（D95）。ユーザーはコードを読まず、品質はエージェントのレビューで保ち、変更の中身は Issue の要約で把握する（D93、D94）。

人の承認の代わりに、main を守る関門を必須チェックにする。CI（`check`、`e2e`）と、実装の文脈を引き継がない新しいセッションのレビュー（`agent-review`）が通った PR だけが、auto-merge される。

人の判断が要るのは、次の2種類だけにする。

- 権限・判断の記録・費用に関わる場所（ワークフロー、ADR と台帳の既存の記述、fly.toml）の変更
- エージェントが止まって needs-decision を付けたとき（台帳や ADR との矛盾、方針や費用に関わる曖昧さ、修正が収束しない、本番で失敗した、など）

## Considered Options

- 人がすべての PR をレビューしてマージする（D15）：ユーザーがボトルネックになり、コードを読まないという目標と両立しない。
- 人の承認を一切なくす：エージェントが自分の権限や判断の記録を書き換えられてしまう。

## Consequences

- レビューの観点は、リポジトリ内で版を管理する。テストを弱める変更は、常に blocking にする。
- 本番のスモークテストが失敗したら、直前のイメージに戻し、revert PR を作って Issue を開き直す。
- 誰がいつ何を変えたかは、Issue の要約と週1回のまとめで追う。
