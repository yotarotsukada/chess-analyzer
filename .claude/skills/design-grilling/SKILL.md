# 台帳を使った設計の grilling

このプロジェクトで設計を決めてきたやり方。ユーザーは判断だけを行い、質問の大半には代理回答のサブエージェントが答える。

## 手順

1. **事実を集める**：設計を左右する事実（料金、ライセンス、API の挙動、規約など）を、調査のサブエージェントに調べさせ、`docs/research/` に出典つきで書かせる。
2. **ユーザーの意向を台帳に書く**：ユーザーが話した方針は、`docs/decisions.md` に出典 `U` で書く。
3. **grilling**：代理回答のサブエージェント（general-purpose）を1つ立て、毎ラウンド次を守らせる。
   - 台帳・CONTEXT.md・ADR を読み直してから答える。台帳と矛盾する答えは「D◯ を覆す提案」と明示する
   - ユーザーにしか決められないことは【要ユーザー判断】と書き、推測で埋めない
   - ファイルは編集しない
   - 各問いに推奨を添えた質問を、まだ決まっていない分岐ごとに出す。答えは出典 `A` で台帳に書く
   - 【要ユーザー判断】は X◯ として台帳に集め、ユーザーに AskUserQuestion で聞く
4. **用語と ADR**：決まった用語はその場で CONTEXT.md に書く。後から変えにくく、理由がないと驚き、実際に比べて選んだ判断は ADR にする（下書きは proposed）。
5. **終える**：未決の分岐が「なし」になったら、決まったことの要約（必要なら提案スライド）をユーザーに見せ、承認をもらう。承認されたら台帳の `A` を「承認済み」にし、ADR を accepted にし、実装を PR 単位の Issue に分ける。

完了条件：台帳に未決の X◯ がなく、ユーザーが承認し、Issue が作られている。

台帳・ADR の編集はユーザーの確認が要る（D120）。grilling 中の追記は、ユーザーが grilling を指示したことで承認済みとみなし、最後の承認でまとめて確かめる。
